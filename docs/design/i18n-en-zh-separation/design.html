i18n — EN/ZH Separation

Lane: full (lightweight)   Status: In-review

Digest

Bottom line — approve this if you agree that: i18n is output-presentation only — Chinese NLU (intent/OLAP/date/alias) and business metadata (metric labels, aliases) stay bilingual/as-is and are not localized — with locale resolved once at the API boundary and default locale zh so current behaviour (and the closeout's validation) is preserved while EN is added.

Change: Separate mixed EN/ZH into a proper i18n layer: symbolic keys with parallel zh/en catalogs, locale from Accept-Language (+ request override), threaded to output nodes only.

Decisions (decision — why — rejected):

  • (A) Scope = output only; NLU + domain data OUT — localizing NLU would break Chinese input handling. Rejected: "extract all Chinese", domain-data localization.
  • (B) Resolve once at API boundary → AgentState.locale → output nodes — single point; generation stays locale-independent. Rejected: per-signature threading, global/context-var.
  • (C) Symbolic keys + zh/en catalogs; backend JSON+resolver, frontend vue-i18n — greenfield, small; no compile step. Rejected: gettext/.po (overkill), inline conditionals (status quo).
  • (D) Default locale zh — preserves every existing output + the closeout's 查询返回 5 行 validation; EN additive. Rejected: default en (churn + breaks sibling).

Risks / watch:

  • Scope boundary is correctness-critical — an NLU string moved to a catalog silently breaks Chinese input.
  • Locale must not leak into schema context / generated SQL (presentation only).
  • Missing key must fall back, never crash.

Open questions:

  • MCP locale surfacing (default zh for now); supported set stays {zh, en}.

Drill down: full design in design.md · tasks in tasks.md.

1. Problem / context

EN/ZH mixed across backend + frontend with no i18n layer (Vue 3, no vue-i18n; no backend gettext/Babel). The CJK strings are three different concerns needing opposite treatment:

CategoryExamplesTreatment
Output / presentationresult summary 查询返回 N 行; semantic block 当前 schema 中没有…; perf hints; frontend UIi18n (this change)
Input / NLUOLAP phrase detection; intent verbs 删除/清空; Chinese date rules; alias matchingNOT i18n — bilingual always
Domain datametric labels 销售额/客单价, aliases, display names; verified queriesmetadata content — not catalog

The trap: "extract all Chinese" would move the NLU patterns and break Chinese input. The scope taxonomy is the design's core value.

2. Goals

In scope: (A) scope taxonomy; (B) locale resolution + propagation to output nodes; (C) catalog mechanism (backend JSON + frontend vue-i18n); (D) default-locale choice.

Out of scope: localizing NLU patterns; localizing domain data; changing generated SQL / schema context / column names; languages beyond zh/en.

3. Key decisions

(A) Scope taxonomy — the crux

Localized: result summary, semantic-guard block, intent blocked message, performance/plan hints, other API messages, all frontend UI chrome. Excluded (must not touch): Input/NLU + Domain-data categories — not presentation; the system accepts Chinese input and carries Chinese business terms regardless of output locale.

(B) Locale resolution + propagation

Resolve once at the API boundary (Accept-Language + request locale override → {zh,en} → default). Carry as AgentState.locale; output nodes read it. Generation is locale-independent — schema context, prompts, SQL unchanged by locale.

(C) Catalog mechanism

Backend backend/app/i18n/{zh,en}.json + resolver t(key, locale, **params) (missing key → fallback → raw key, logged). Frontend vue-i18n with zh/en message files; UI switcher persisted in localStorage, locale sent to backend. Independent per-layer catalogs, shared key convention.

(D) Default locale = zh

Existing Chinese output stays identical with no locale supplied; current tests + the sibling closeout validation hold. EN is additive — dissolves the coupling.
